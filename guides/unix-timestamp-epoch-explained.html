Unix Timestamp & Epoch Time Explained

A Unix timestamp is just a count of seconds since 1970-01-01 00:00:00 UTC — no date, no timezone, no formatting. This covers what that number actually is, how to tell seconds from milliseconds at a glance, why "UTC by definition" is the entire point, what breaks in 2038, and how to get "now" as epoch across five languages.

reference guide UTC cross-language

// what a Unix timestamp actually is

│

A Unix timestamp is a single number: the count of seconds elapsed since 1970-01-01 00:00:00 UTC. That instant is "the epoch," and it is the only thing the number is measured against — there is no date, no timezone, and no formatting stored anywhere in the value. 0 is the epoch itself. 1000000000 is 2001-09-09. Ten-digit values like 1788108484 are the present day. The same number means the same instant on every machine on Earth, which is the entire reason the format exists.

// seconds or milliseconds? count the digits

│

Unix time is defined in seconds, but a great deal of software — JavaScript most prominently — hands you milliseconds instead. Since a millisecond value is the second value multiplied by 1000, it simply carries three more digits, and that is the fastest reliable way to tell them apart at a glance.

// what happens when the unit is wrong

  • Seconds read as milliseconds — the value is treated as 1000× smaller than intended, so it lands in January 1970, a few days after the epoch. This is the classic "why is every date showing 1970" bug.
  • Milliseconds read as seconds — the value is treated as 1000× larger, throwing the date tens of thousands of years into the future. Some systems reject it outright; others cheerfully display an absurd year.
Neither mistake throws an error at the boundary where it happens — both produce a perfectly valid number that is simply wrong, and the damage usually surfaces much later in a report or a UI. Check the unit at every boundary a timestamp crosses, not just once at the source.

// why "UTC by definition" is the whole point

│

A Unix timestamp has no timezone attached because it doesn't need one — it's a count of seconds from a single fixed instant, so 1735689600 means the exact same moment everywhere on Earth. The timezone only re-enters the picture when you convert it to a human-readable string for display. This is precisely why storing timestamps as epoch (or any UTC value) and converting to local time only at the display layer is the correct default — the alternative, storing "local wall-clock time," runs straight into a problem epoch time was designed to avoid entirely.

Local wall-clock time is ambiguous twice a year. During a "spring forward" DST transition, a clock jumps from 1:59 AM straight to 3:00 AM — the local time 2:30 AM never happens that day. During "fall back," 1:00–1:59 AM occurs twice — a stored local timestamp of 1:30 AM doesn't say which occurrence it means. Neither problem can happen to a Unix timestamp, because it isn't wall-clock time — it's a single, unambiguous instant. A scheduled job or event stored as local time can silently fire twice, not at all, or at the wrong hour on transition days; the same job stored as epoch/UTC never has this failure mode.

Handing a JavaScript timestamp to a backend that expects seconds is the single most common source of the unit bug described above.

// leap seconds: ignored by design, not by accident

│

Real UTC occasionally inserts a leap second to stay aligned with Earth's slightly irregular rotation. POSIX time explicitly does not count them — the standard defines every day as exactly 86,400 seconds, full stop. When a leap second is inserted in reality, Unix time either repeats a second or is adjusted by the OS ("smeared" across the surrounding hours) depending on the system — either way, the raw count quietly diverges from true elapsed seconds by design, not by bug. As of 2025, 27 leap seconds have accumulated since 1972; international standards bodies (BIPM) have agreed to stop inserting new ones by 2035, with a final vote expected in 2026, which will freeze this drift rather than reverse it.

In practice this almost never matters for application code — it's a fact worth knowing exists, not something to write handling logic for. It explains why "elapsed real-world seconds" and "difference between two Unix timestamps" aren't perfectly identical concepts at the margins, which occasionally matters for scientific/astronomical timing systems but essentially never for web applications.

// the year 2038 problem

│

A signed 32-bit integer tops out at 2147483647, which as a Unix timestamp is 2038-01-19 03:14:07 UTC. One second later the value overflows, and on a system that still stores time that way it wraps to a large negative number — 1901-12-13. That is the same class of bug as Y2K, with the same fix: use a wider type.

Modern platforms have largely dealt with this. 64-bit builds of Linux, current .NET (DateTimeOffset), Java, Python, and JavaScript all use 64-bit or floating-point representations that push the limit far past any practical horizon. The remaining exposure is in specific places: 32-bit embedded systems, older C code using a 32-bit time_t, and database columns explicitly typed as a 4-byte integer — MySQL's TIMESTAMP column type being the one most likely to appear in an ordinary web stack.

// epoch vs. ISO 8601 — different tools for different jobs

trade-offs
Epoch (number)compact, sorts correctly as a number, not human-readable, unit ambiguity (s vs ms)
ISO 8601 (string)human-readable, sorts correctly as a plain string too, timezone-explicit, more bytes
│

ISO 8601's field order (year → month → day → hour...) means lexicographic string sorting matches chronological order — a rare and genuinely useful property, which is why log files and filenames often use it. Epoch numbers sort correctly too, but only when compared as actual numbers; naively comparing them as zero-padded strings of different lengths breaks the same way any numeric string comparison does. Pick epoch for compact storage and arithmetic (durations, comparisons), ISO 8601 for anything a human will read directly — logs, API responses meant for debugging, config files. This same sortability is why UUIDv7 embeds an epoch millisecond timestamp directly in the identifier — see UUID/GUID Versions Explained for why that matters for database index performance.
