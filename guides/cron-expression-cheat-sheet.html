Cron Expression Cheat Sheet

Cron syntax looks cryptic until you've memorized it, then you forget it again the moment you switch jobs. This is the reference: every field, both major dialects, and the mistakes that pass validation but run at the wrong time.

reference guide Hangfire Quartz.NET

// the two dialects

│

Almost every scheduler you'll meet uses one of two cron dialects. Standard cron (what Hangfire, Linux crontab, and most CI systems use) has 5 fields: minute, hour, day-of-month, month, day-of-week. Quartz.NET adds a leading seconds field and uses ? instead of * in whichever of day-of-month/day-of-week isn't in use — 6 fields total (a 7th, optional year field also exists but is rarely set).

field order
Standard / Hangfire (5 fields)minute hour day-of-month month day-of-week
Quartz.NET (6 fields)second minute hour day-of-month month day-of-week

// special characters

syntax
*every value in this field
,a list — MON,WED,FRI
-a range — 9-17 means 9 through 17
/a step — */15 means every 15 units, starting at 0
?"no specific value" — Quartz.NET only, used on whichever of day-of-month/day-of-week you're not constraining
L"last" — Quartz.NET only; last day of the month, or last given weekday
#"nth weekday of the month" — Quartz.NET only; 6#3 = third Friday

// combining ranges and steps

│

The characters above compose — a step can apply to a range instead of the whole field, which is where most of cron's real expressive power (and most misreadings) live.

examples
10-30/5every 5 units, but only between 10 and 30 — fires at 10, 15, 20, 25, 30, not before or after
MON-FRIa named range — equivalent to 1-5 in most implementations, but check yours accepts names
0,30a list of two exact values — fires at :00 and :30, not a range
1-5,10-15multiple ranges in one field, comma-separated

The step always starts counting from the beginning of whatever range it's attached to — 10-30/5 starts at 10, not at 0 clipped to the range. This is the same rule as a bare */5 starting at the field's zero point, just applied to a sub-range instead of the whole field.

examples

// mistakes that pass validation but run wrong

Setting both day-of-month and day-of-week to specific values doesn't mean "AND" — in standard cron it means "OR" (either condition triggers it), which almost never matches what you intended. If you want a specific weekday, leave day-of-month as *.
Day-of-week numbering differs by dialect: standard cron is 0–6 with 0 = Sunday. Quartz.NET is 1–7 with 1 = Sunday. The same digit means a different day depending which dialect you're reading — always check which one you're in before trusting a number.
Cron expressions run in whatever timezone the scheduler process is configured for — not necessarily UTC, and not necessarily the server's local time if the app sets one explicitly. A schedule that looks right can drift by hours after a timezone or daylight-saving change if this isn't pinned down.
A step value like */5 always starts counting from the field's zero point, not from "5 units from now." */5 on minutes fires at :00, :05, :10 — never at :02, :07, :12, no matter what minute you deployed at.

// pinning down the timezone

│

A cron string has no timezone of its own — it's just field values, interpreted against whatever clock the scheduler evaluates it with. That clock is a separate, easy-to-miss setting, and getting it wrong doesn't throw an error; the job just quietly runs at the wrong wall-clock time.

where the timezone actually gets set
HangfireRecurringJob.AddOrUpdate(..., cron, new RecurringJobOptions { TimeZone = TimeZoneInfo.FindSystemTimeZoneById(...) }) — omit it and Hangfire schedules in UTC
Quartz.NETCronScheduleBuilder.CronSchedule(expr).InTimeZone(TimeZoneInfo...) — omit it and Quartz uses TimeZoneInfo.Local, i.e. whatever the host machine is set to

That default mismatch — Hangfire falling back to UTC, Quartz falling back to the host's local time — is itself a common source of "this ran three, four, or five hours off" bugs when a job moves between a developer's machine, a container, and a cloud region without the timezone ever being set explicitly on either side. Pin it explicitly in code rather than relying on either default, and remember that a timezone with daylight saving (unlike UTC) means the same cron expression covers a different number of real hours on the two days each year the clock shifts.

// Cron helper methods vs raw expressions (Hangfire)

│

Hangfire's Cron class ships a set of static helpers that return a cron string for the common cases, so most recurring jobs never need a hand-written expression at all.

Hangfire.Cron helpers
Cron.Minutely()→ * * * * *
Cron.Hourly()→ 0 * * * *
Cron.Daily(2, 30)→ 30 2 * * *
Cron.Weekly(DayOfWeek.Monday, 6)→ 0 6 * * 1
Cron.Monthly(1)→ 0 0 1 * *

The helpers exist because a call like Cron.Daily(2, 30) is self-documenting at the call site in a way "30 2 * * *" never is, and it can't be typo'd into a subtly different valid expression. Reach for a raw string only once a schedule needs something the helpers don't cover — a step value, a multi-day list, or anything Quartz-specific like L/W/# — and paste it into the Cron Builder first to confirm it means what you think before it ships.
